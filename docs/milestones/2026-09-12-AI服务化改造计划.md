# 本机 AI 服务化改造（Node 后端 + KataGo 外部引擎）

## 目标

- 本机运行 Node 后端并调用本机已安装的 KataGo 可执行文件提供 AI 围棋服务；局域网设备只做客户端，**不再加载任何 AI 模型**。
- 本机与局域网**统一走该服务**：人机对弈与回放分析均通过 HTTP 调用后端，浏览器端 TF.js 推理路径下线（代码保留、不再被 `main.ts` 引用）。
- 后端支持：模型**加载/卸载/切换**、**运行状态查看**、**并发与限流**。
- KataGo 可执行路径与模型清单通过**配置文件/环境变量**指定；管理面板只负责加载/卸载/切换与查看状态。

## 架构总览

```
本机/局域网浏览器 (src/, 不加载模型)
   │  HTTP  /api/ai/*   (think 单次 JSON / analyze NDJSON 流)
   │  HTTP  /api/models|status|health
   ▼
Node 后端 (server/，新增)  ── spawn ──▶  katago analysis（JSON 行协议，每模型一进程）
   • EngineManager：模型注册、加载/卸载/切换、状态、并发队列限流
   • 生产环境同时静态托管 dist/
```

- 开发：Vite(:5173, 已 `host:true`) 提供前端，`/api` 代理到后端(:8080)；局域网设备访问 Vite 打印的 Network 地址。
- 生产：`node server/index.ts` 同时托管 `dist/` 与 `/api`，局域网设备访问 `http://<本机IP>:8080/`。

## 坐标与协议约定（关键）

- 客户端 ↔ 后端统一使用棋盘索引 `pos = row*19 + col`（row 0 在上），`pos = 361` 表示虚着。后端独占与 KataGo 文本坐标的互转，客户端不感知 KataGo 坐标。
- 转换：`letter = COLUMN_LABELS[col]`（`'ABCDEFGHJKLMNOPQRST'`，跳过 I），`num = 19 - row`；虚着 `"pass"`。`(col,row)` 语义对齐 `src/core/board.ts` 的 `idx` 与 `src/ui/board-renderer.ts` 的 `COLUMN_LABELS`。
- 请求携带**从空盘起的完整手顺**：`moves: { stone: 'B' | 'W'; pos: number | null }[]`，加 `komi`、`rules: 'chinese'`。
- 候选与变化线直接取自 KataGo 响应的 `moveInfos`：`moveInfos[i].move` → `pos`，`moveInfos[i].pv` → `pv: number[]`（长度由生成的 analysis 配置 `analysisPVLen = 15` 决定），胜率用 `winrate`、`visits`、`scoreLead`、`prior`。

## 后端（新增 `server/`）

- `server/config.ts`：`ServerConfig` 类型与 `loadConfig()`，优先级 env > `ai.config.json` > 默认值。
  - 字段：`port`(8080)、`host`(0.0.0.0)、`katagoPath`、`modelDir`、`models: {id,name,file}[]`、`activeModel`、`maxVisitsDefault`、`numAnalysisThreads`、`nnMaxBatchSize`、`reportDuringSearchEvery`、`analysisPVLen`、`maxInFlightPerEngine`(1)、`maxQueuePerEngine`(8)、`queueTimeoutMs`、`requestTimeoutMs`。
  - env：`KATAGO_PATH`、`KATAGO_MODEL_DIR`、`AI_PORT`、`AI_ACTIVE_MODEL`。
- `server/engine/coords.ts`：`posToKataGo(pos)` / `kataGoToPos(s)`，`PASS = 361`（与 `src/engine/mcts.ts` 的 `PASS` 数值一致）。
- `server/engine/protocol.ts`：构造 analysis 查询（`{ id, moves, rules, komi, boardXSize:19, boardYSize:19, maxVisits, reportDuringSearchEvery }`）与解析响应为内部 `{ candidates, rootWinrate, rootScoreLead, visits }`；`think` 复用同一响应取最优着法。
- `server/engine/analysis-config.ts`：由 `ServerConfig` 生成临时 KataGo `analysis` 配置（`numAnalysisThreads`、`nnMaxBatchSize`、`maxVisits`、`reportDuringSearchEvery`、`analysisPVLen`），写入临时文件供 `-config` 使用。
- `server/engine/katago-process.ts`：`NodeKatagoProcess`——`spawn(katagoPath, ['analysis','-config',cfg,'-model',modelPath])`；stdin 写 JSON 行、stdout 按行解析并按 `id` 匹配 Promise；stderr 收集为日志；`spawn` 通过依赖注入以便单测用假进程。
- `server/engine/engine.ts`：`EngineInstance`——绑定一个模型，持有进程、状态（`starting|ready|busy|error|stopped`）、`inFlight/queued/rejected/totalRequests/startedAt/lastError`；内置 FIFO 队列与限流（`maxInFlightPerEngine`/`maxQueuePerEngine`/超时）；入队满返回 429；启动后执行一次 warmup 查询确认 `ready`。
- `server/engine/manager.ts`：`EngineManager`——模型注册表、`load(id)`/`unload(id)`/`activate(id)`、`status()`（各实例状态 + 全局队列统计 + 只读的 `katagoPath`/`modelDir`）、`run(modelId, request)` 路由到实例。
- `server/api.ts`：路由
  - `GET /api/health` → `{ ok, katagoPath, katagoVersion, activeModel }`
  - `GET /api/models` → `{ models:[{id,name,path,sizeBytes}], active }`
  - `GET /api/status` → `{ engines:[...], active, queue:{...}, config:{paths...} }`
  - `POST /api/models/:id/load` / `POST /api/models/:id/unload` / `POST /api/models/:id/activate`
  - `POST /api/ai/think` → JSON `{ move:number, winRate, scoreLead, visits }`
  - `POST /api/ai/analyze` → **NDJSON 流**：每次 `reportDuringSearchEvery` 回报一行 `{ playouts, rootValue, bestMove, candidates:[{pos,visits,winRate,scoreLead,prior,pv}] }`；客户端断开（`AbortController`）即取消查询并释放槽位。
- `server/static.ts`：`dist/` 静态托管（生产）。
- `server/http.ts` + `server/index.ts`：`node:http` 服务、JSON/NDJSON 辅助、路由分发、启动 `EngineManager`。
- `src/engine/remote/protocol.ts`（共享类型，仅 `import type`，不产生运行时代码）：`AiMoveRequest`、`AnalyzeSnapshot`、`CandidateWire`、`ServiceStatus` 等，供客户端与后端共用。

技术要点：Node v25 原生支持 TS 类型剥离，直接用 `node server/index.ts` 运行（无需编译），本地导入需带 `.ts` 后缀；新增依赖仅 `ws` 之外的零运行时依赖（本方案用 `node:http`，**不新增运行时依赖**）。

## 前端改造

- 新增 `src/engine/remote/service-client.ts`：`fetch` 封装 `/api/health|models|status`、`POST think`、`POST analyze`（`resp.body.getReader()` 按行解析 NDJSON，`AbortController` 取消）。
- 新增 `src/engine/remote/remote-ai-player.ts`：`RemoteAiPlayer`，保持与 `AiPlayer` 相同对外形状（`isReady`、`backendLabel`、`thinking`、`think(game, level)`），内部把 `game.getMoves()` 序列化为 `moves`，按难度档位传 `maxVisits` 与温度采样（复用现有 `AI_LEVELS` 定位，将 `playouts` 语义映射为 `maxVisits`/`maxTemperature`）。
- 新增 `src/engine/remote/remote-analysis.ts`：`RemoteAnalysisClient`，保持与 `AnalysisClient` 相同回调形状（`ensure()`、`analyze(state)`、`callbacks.onSnapshot`），把回放视角转为 `moves`+`komi` 请求；`stop()` 通过 `AbortController` 中断。
- 修改 `src/main.ts`：
  - 替换导入：不再引入 `model-loader`/`ai-player`/`analysis-client`（及其 `MODEL_B18`、`LoadPhase`），改用 remote 版本；删除 `loadAiModel`、下载/导入模型、`getCachedModelBytes`、`file input`、`load-bar` 等浏览器模型逻辑。
  - `analysisState()` 改为基于 `replay.lineMoves().slice(0, pos)` 构造 `{ moves, komi:KOMI_AREA }`。
  - 候选点击不再走 `requestVariation`，直接用 `candidate.pv` 作为 `variationLine`（15 步内）渲染；`renderCandidateList` 适配新字段（`winRate`/`visits`）。
  - 新增「AI 服务」面板（替换现有「AI 模型」面板）：显示服务连接状态、只读的 KataGo 路径/模型目录、模型列表与当前激活项、每个运行实例状态（state/pid/inFlight/queued/requests/lastError）、以及「加载 / 卸载 / 设为默认」按钮；每 2s 轮询 `/api/status`。
  - `maybeAiMove()`、`refresh()` 状态文案（如「AI 思考中…」）适配远端；服务不可用时给出明确提示并保持双人/SGF 功能可用。
- `src/styles.css`：为服务面板与状态徽标补充样式。
- 保留 `src/engine/{net,weights,mcts,features,backend,analysis-engine,analysis-worker,analysis-client,ai-player,model-loader}.ts` 与 `src/core/*` 不动（含其单测），仅停止在 `main.ts` 中引用；后续可另行清理。

## 假设与注意

- 本机当前**未安装 KataGo**（PATH、`/usr/local/bin`、`/opt/homebrew/bin` 均无）；需先安装并在 `ai.config.json` 配置可执行路径与模型文件，否则服务以「未就绪」降级（仅提示，不崩溃）。
- 沿用项目现有 `KOMI_AREA = 3.75`（`src/core/scoring.ts`）作为 KataGo `komi`，与既有 `features.ts` 输入及本盘计分一致（属项目既有约定，非标准 7.5 目）；该值在配置中可改。
- 变化线由 KataGo `moveInfos[i].pv` 直接提供，**不再需要**自行 `searchVariation` 与 `/api/ai/variation`。
- 并发默认按每实例 `maxInFlight=1`、`maxQueue=8`；分析流占用槽位期间对弈请求会排队，客户端离开回放/开始对弈时会主动取消分析流。

## 复盘：为什么上线后才发现「漏装了 KataGo 程序」

服务化改造完成、单测/构建全绿、服务也能正常启动，但用户在页面上点「人机对弈」时才暴露 `spawn /usr/local/bin/katago ENOENT`——本机根本没装 KataGo 可执行程序。根因如下：

1. **把「安装 KataGo」当成了外部前置条件，而非交付项。** 本计划「假设与注意」里已写明「本机当前未安装 KataGo，需先安装」，等于把安装划到了实现范围之外（假设由用户完成）。但这条假设从未被闭环确认，也没有对应的安装/验收步骤，最终被默认「以后再说」而遗漏。
2. **优雅降级掩盖了缺口。** 「缺 KataGo 不崩溃、只降级」是刻意的设计优点，但副作用是所有自动化验证都能通过：单测用**依赖注入的假 spawn**、`npm run build` 只做类型检查、冒烟只验证「服务能起 + 能降级」，**真实 `spawn('katago')` 代码路径零覆盖**，缺口不会在任何一道门禁里暴露。
3. **缺少针对真实引擎的端到端验收。** 验证止步于「服务启动」，没有「真正从 KataGo 拿到一手合法着法」的 acceptance 步骤；直到人工点人机对弈才触发。
4. **旧架构的心智模型 + 只存在权重文件的误导。** 浏览器 TF.js 时代，导入 `.bin.gz` 即可下棋（权重本身就是「可运行的模型」）。`~/Downloads` 里恰好留有旧权重，造成「该有的都有了」的错觉；但新架构里 `.bin.gz` 只是 **KataGo 的输入参数**，真正跑 AI 的是**程序**——这是一个全新、且旧架构没有对应物的依赖，极易被漏掉。
5. **交付物从「一个」变成「两个」。** 旧：模型文件（1 个）。新：**KataGo 程序 + 模型文件**（2 个）。文档虽都提到，但「装程序」这一步没有像「放模型」那样有可操作的落地脚本或检查项。

**改进措施：**
- 启动日志已探测并打印 `[未检测到]`，`/api/status` 暴露 `lastError: ENOENT`，便于快速定位（本次即靠此定位）。
- 安装 KataGo 纳入交付：macOS 用 `brew install katago`（Intel/Apple Silicon 均可），并在 `ai.config.json` 配置 `katagoPath`。
- 建议补一条「真实引擎冒烟」脚本/CI（装了 KataGo 时跑一次 `think` 断言返回合法着法），把这条真实路径纳入回归门禁。
- 文档明确「两个交付物」的区分（见 `docs/architecture/backend.md` 运行前置一节）。

## 复盘（续）：装好 KataGo 后仍 `SIGABRT` —— 精简配置缺必填键

装上 KataGo v1.18.2（因本机 Intel + macOS 属 Homebrew Tier 3、且 brew 校验 Xcode 版本，最终用 cmake + CLT clang 源码编译部署到 `/usr/local/bin/katago`）后重启，`/api/status` 仍显示引擎 `error`、KataGo 进程启动即 `SIGABRT`。手动复现 `katago analysis` 抓到真实报错：

```
libc++abi: terminating due to uncaught exception of type IOError:
Could not find key 'numSearchThreads' in config file
```

**根因**：`renderAnalysisConfig` 生成的临时配置只写了 `numAnalysisThreads` 等精简键，但 KataGo analysis 模式**同时要求 `numSearchThreads`**，缺失即抛未捕获异常终止进程。这与「漏装程序」同源——**单测用的是假进程，凡是只有真实二进制才校验的约束（必填配置键、参数格式）都不被覆盖**，所以构建/测试全绿依旧会漏。

**修复**：`ServerConfig` 新增 `numSearchThreads`（默认 `4`，同步 `ai.config(.example).json`），`renderAnalysisConfig` 写出该键；手动喂一手确认 KataGo 正常返回着法（Q16、winrate、scoreLead）。这也再次印证「改进措施」里的**真实引擎冒烟**必要性——它是唯一能拦住此类问题的门禁。

## 复盘（续二）：komi 非半整数被拒 → AI 每手虚着

引擎 ready 后人机对弈中 AI 仍每手虚着、日志无异常。根因与 `numSearchThreads` 同源——都是「只有真实二进制才校验」的约束：本项目内部贴子 `KOMI_AREA = 3.75`（标准中国数子贴子），但 KataGo 只接受整数/半整数 komi，传 3.75 被拒且返回空 `moveInfos`，`parseThink` 把空候选当作 PASS。修复：新增 `sanitizeKomi` 兜底并对带 `error` 的响应直接 reject。

**最终决定**：为使最终结算与 AI 评估严格一致（消除 3.75 vs 4.0 的 0.25 目偏差），将 `KOMI_AREA` 从 3.75 改为 KataGo 合法的半整数 **3.5**，评分 / think / analyze 三处共用该常量；同步修正结果面板硬编码贴子文案与 SGF 导出未写入真实 komi（`KM` 恒为 7.5）的问题。
